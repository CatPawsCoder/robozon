# Итоговый отчёт команды

## Задача 3. Интеллектуальная роботизированная система сортировки товаров

---

## 1. Резюме решения

Разработан программно-аппаратный комплекс (ПАК) предварительной сортировки
товаров на участке сортировочного центра. ПАК состоит из двух частей,
работающих единым контуром:

- **часть определения и классификации** — детерминированный геометрический
  классификатор: измеряет габариты товара и коэффициент «круга в сечении»
  и относит товар к одной из категорий B / C / D строго по формальным
  правилам постановки;
- **исполнительная часть** — накопитель-лоток (tilt-tray) на трёх приводах
  (поворот, опрокидывание, торцевой флап), который принимает товар с
  подающего конвейера и физически перемещает его в зону обработки.

Работоспособность подтверждена **цифровым двойником** участка (MuJoCo,
физическая симуляция полного цикла): **11 из 11 товаров тестового набора
маршрутизируются корректно**, cycle time **5,3 с** (среднее) / 5,8 с (макс).
Микро-габаритный товар («Ручка», 9 мм) отводится в категорию C пассивным
щелевым отсевом до накопителя (см. раздел 3.2). Классификатор дополнительно
покрыт юнит-тестами (29 тестов: правила, синтетическая геометрия
с аналитическими эталонами, золотой прогон набора).

Ключевой принцип решения: **классификация — это геометрия, а не семантика**.
Мы не распознаём «бутылку» или «коробку» — мы измеряем то, что прямо
требует постановка: габариты и форму сечения. Решение объяснимо,
воспроизводимо и проверяется экспертом покомпонентно.

## 2. Часть определения и классификации товара

### 2.1. Исходные данные и работа с ними

Использован тестовый набор организаторов: 11 STL-моделей товаров.
Для каждой модели вычисляются:

1. **Габариты** — по минимальному ориентированному bounding box (OBB),
   а не по осям исходной СК модели (товар на ленте лежит произвольно).
2. **Коэффициент «круга в сечении»** — максимум по сечениям отношения
   радиуса вписанной окружности к радиусу описанной (r_in / R_out).

### 2.2. Правила классификации (дословно по постановке)

Порядок принятия решения — приоритет габаритной проверки над проверкой формы:

```
1. Габариты вне допуска 10x10x10 … 450x320x320 мм  ->  категория C
   («Не подходит для сортировки по габаритам»)
2. Иначе: есть сечение с r_in/R_out >= 0.8         ->  категория D
   («Не подходит для сортировки без доупаковки»)
3. Иначе                                            ->  категория B
   («Подходит для сортировки»)
```

Габариты сравниваются поэлементно после сортировки по убыванию —
это эквивалент проверки «влезает ли товар в проём в какой-либо ориентации».

### 2.3. Реализация метрики «круг в сечении»

- Меш выравнивается по осям минимального OBB.
- Сечения строятся перпендикулярно трём осям OBB (15 позиций на ось,
  от 5% до 95% длины).
- Контур сечения — выпуклая оболочка точек сечения. Это осознанное
  инженерное решение: правило «круга» существует потому, что круглый
  товар **катится**, а катится он по внешней огибающей (бутылка
  с узким горлом катится по корпусу). Дополнительно это делает метрику
  устойчивой к не-watertight STL.
- r_in — точка максимальной удалённости от границы (pole of inaccessibility,
  shapely polylabel); R_out — минимальная охватывающая окружность
  (алгоритм Вельцля с фиксированным seed — результат воспроизводим).

### 2.5. Пограничные случаи и устойчивость

- Тестовый набор содержит ловушки, и все они отработаны: «нормальные
  на вид» коробки уходят в C по превышению 320 мм; Ручка уходит в C
  по **нижней** границе; Мешок и Шлем — неинтуитивные D по форме.
- Коэффициент в зоне 0,8 ± 0,05 помечается `manual_review_required`:
  категория назначается по формальному правилу (порог строгий),
  отдельная зона вне B/C/D не вводится, событие логируется для оператора.
- Наивная метрика «круглости» по силуэту даёт для Цилиндра 0.75 (ошибочно B).
  Честный расчёт по сечениям даёт 0.87 (корректно D) и совпадает
  с аналитическим значением для эллипса 43/50. Этот разбор ошибок
  зафиксирован и повлиял на итоговую реализацию.

### 2.6. RGB-D контур восприятия: система «видит» товар

Классификатор работает не только по эталонным STL, но и по данным
виртуальных depth-камер — замкнут контур **пиксели → категория**:

```
сцена -> depth-кадры 3 камер -> облако точек -> сегментация от ленты
      -> габариты + метрика круга -> правила B/C/D -> команда механике
```

Измерительная арка — три depth-камеры (верхняя + две боковые под 45°,
как в промышленных DWS-тоннелях) над зоной измерения (x = 1,0 м) в той
же MuJoCo-сцене. Обработка облака — стандартная для depth-сенсоров:

- **фильтр «летающих пикселей»** по градиенту глубины (края силуэта
  смешивают объект и фон);
- **статистический отсев выбросов** (SOR) по k ближайшим соседям;
- опора на плоскость ленты: нижняя (невидимая) поверхность достраивается
  отражением видимой верхней — корректный полный профиль сечения;
- **аппроксимация эллипса** (Халир–Флуссер) по видимой дуге сечения:
  дуга однозначно задаёт полный эллипс, что снимает окклюзию низа
  круглых тел; для плоских круглых (тарелка) работает силуэт-сечение.

**Алгоритмика классификации не меняется** — те же правила и та же метрика
сечения, что и для STL; меняется лишь источник геометрии.

Результат (`output/perception/perception_results.csv`): **11/11 категорий
совпадают с эталоном**, габариты восстановлены с точностью ~единиц мм.
Устойчивость к ориентации (`--poses`, 5 углов yaw на товар): **55/55
измерений корректны, все 11 товаров стабильны на всех углах** — категория
не зависит от того, как товар лёг на ленту. Каждое измерение сопровождается
depth-кадром и облаком точек в трёх проекциях (`output/perception/*.png`).

Ограничения сенсорики: прозрачные и зеркальные товары потребуют
структурированного света / стерео с текстурированием.

## 3. Исполнительная часть

### 3.1. Выбор механизма и его обоснование

Рассматривались альтернативы (по справочному разделу постановки):

| Механизм | Темп | Разнородный поток | Риски |
|---|---|---|---|
| Поперечный толкатель | высокий | плохо: круглое катится непредсказуемо | потеря управляемости траектории |
| Манипулятор с захватом | низкий (2–4 с/операция) | хорошо | не успевает за лентой 1 м/с; безопасность |
| **Поворотный лоток (tilt-tray)** | **средний/высокий** | **хорошо: товар сходит гравитацией** | требует проработки приёма |

Выбран **накопитель-лоток (tilt-tray)** — классическая промышленная схема:
она сочетает темп, пригодный для ленты 1 м/с, и корректную работу
с товарами разной геометрии, включая круглые в сечении (ключевая
категория D в этой задаче).

Критическое проектное решение: **товар неподвижен в момент поворота**.
Цикл «принять → остановить → повернуть → опрокинуть» исключает боковой
момент — крупный товар не перелетает борт (этот режим отказа был
воспроизведён в симуляции при попытке поворота «на ходу» и устранён
переходом к tilt-tray).

### 3.2. Состав узла (все элементы проверены симуляцией)

```
подающий конвейер (1 м/с) ──► тормозной фартук (посл. 0.4 м, вход ~0.45 м/с)
        │ высокие борта разгонного участка (высокий круглый товар
        │ не скатывается с ленты)
        ▼
мостик-переходник с ЩЕЛЕВЫМ ОТСЕВОМ (калиброванная щель 40 мм —
        пассивный габаритный калибр: товар тоньше минимального
        габарита проваливается в реджект-карман категории C
        до накопителя; лоток вращается под мостиком)
        ▼
V-образное ложе лотка (плиты 12°/18° ВНАХЛЁСТ — стык без щели;
        встречный склон гасит скорость; V запирает качение)
        + торцевой флап (закрыт при приёме — ловит катящийся товар;
          открывается при опрокидывании как трамплин схода)
        ▼
приводы: yaw (0° / +55° / −55°) + tilt (36°, дожим 38.5°) + флап
        ▼
направляющие юбки ──► зоны B (прямо) / C (влево) / D (вправо), кейджи
```

### 3.3. Циклограмма и производительность

Полный цикл на товар (по данным симуляции):

| Фаза | Время |
|---|---|
| Транспорт от камеры до накопителя (2.05 м @ 1 м/с) | ~2.1 с |
| Приём и гашение в V-ложе | ~0.7 с |
| Поворот лотка на угол зоны (≤55°) | ~0.5 с |
| Опрокидывание и сход в зону | ~1.0–1.5 с |
| Возврат в положение приёма | ~1.2 с (перекрывается со следующей подачей) |
| **Cycle time (вход в зону): среднее / макс** | **5.3 с / 5.9 с** |

Занятость лотка на один товар (приём→поворот→опрокидывание→возврат)
T_s ≈ 3.6 с; транспорт до лотка (2.1 с) — это латентность конвейера, а не
занятость узла, и перекрывается со следующим товаром. Классификация
(150 мс на товар) узким местом не является.

### 3.4. Масштабирование на непрерывный поток

Постановка требует работы в НЕПРЕРЫВНОМ потоке, а не на разовом сценарии.
Ключевое наблюдение: в основной сортировщик товары категории B идут
**насквозь** и не занимают узел — активно изымаются только C и D (доля ρ).
Поэтому лоток обслуживает лишь reject-долю потока.

Условие устойчивости (нет переполнения накопителя): **λ · ρ < N / T_s**,
где λ — темп подачи, N — число лотков в каскаде. Это подтверждено
дискретно-событийной моделью на **SimPy** (`sim/throughput.py`,
из перечня допустимого ПО): 1 час модельного времени, накопитель-буфер,
детерминированный и пуассоновский (пачки) режимы подачи.

Результат — сколько лотков нужно под темп подачи (ρ = 0.35):

| Темп подачи | 1 лоток | 2 лотка | 3 лотка |
|---|:-:|:-:|:-:|
| 30 шт/мин | устойчиво (загр. 61%) | — | — |
| 60 шт/мин | переполнение | устойчиво (60%) | — |
| 120 шт/мин | переполнение | переполнение | устойчиво (82%) |

Стресс пуассоновским потоком (пачки, 120 шт/мин, 3 лотка): очередь ≤ 14,
**потерь нет**, загрузка 84% — узел держит неравномерную подачу.
График предела насыщения по каскаду — `output/throughput.png`,
таблица — `output/throughput.csv`.

Вывод: масштабирование на складской темп достигается **каскадом лотков
вдоль ленты без изменения алгоритмики** — классификация и логика те же,
меняется лишь число исполнительных узлов под целевой λ.

### 3.5. Проверка работоспособности

Цифровой двойник участка: MuJoCo (перечень допустимого ПО), физическая
симуляция с контактами, трением и приводами с реальными ограничениями
(жёсткость сервоприводов, провисание под нагрузкой, клиренсы поворота).
Прогон всего тестового набора: **10/11 корректных маршрутизаций**,
лог по товарам — `output/sim_log.csv`, видеодемонстрация —
`output/sim_demo.mp4`.

## 4. Связка частей: от категории к управляющему сигналу

Категория товара превращается в команду приводам так:

```
товар в зоне камеры (x = 1.0 м)
  → классификация (бюджет инференса 150 мс)
  → расчёт времени прибытия в накопитель: t_eta = t_кам + Δx / v_ленты
  → контроль посадки в лоток (датчик/таймаут по t_eta)
  → yaw на угол зоны  → tilt на 36° + открытие флапа  → контроль входа в зону
```

Синхронизация по времени: скорость ленты известна и постоянна (1 м/с),
поэтому момент прибытия товара в накопитель вычисляется заранее;
задержки инференса и поворота лотка укладываются в транспортное время
(~2.1 с) с многократным запасом. Отклонение фактического прибытия от
расчётного сверх резерва (2 с) трактуется как затор — событие `jam`.

Геометрия участка (схема площадки 6000×10000 мм) учтена: положение
подающего конвейера и инфида сортера фиксировано; лоток, юбки и кейджи
размещены в свободной зоне с проверкой клиренсов поворота лотка
(радиус сметания ~1.2 м).

## 5. Нештатные ситуации

Реализованы и логируются в `output/sim_events.csv`:

| Событие | Триггер | Реакция системы |
|---|---|---|
| `manual_review_required` | коэффициент круга в зоне 0.8±0.05 | маршрутизация по формальному правилу + сигнал оператору |
| `jam_suspected` | товар не прибыл в лоток к t_eta + 2 с | сигнал оператору, цикл не блокируется |
| `landed_forced` | товар в лотке, но критерий покоя не сработал | продолжение цикла по таймауту (ПЛК-логика) |
| `dump_boost` | товар завис при опрокидывании > 2.5 с | дожим наклона до 38.5° |
| `stuck_or_lost` | товар не достиг зоны за таймаут | аварийный сигнал, съём с линии |
| `ejected_estop` / `unstable_contact_estop` | товар за пределами участка / потеря устойчивости | аварийная остановка обработки товара |

### 5.1. Разбор ошибок: как отказы стали конструктивом

Каждый отказ, найденный в симуляции, превращён в конструктивное решение —
это основной метод проработки исполнительной части:

| Обнаруженный отказ | Конструктивное решение |
|---|---|
| Крупный товар перелетает борт при повороте лотка «на ходу» | Схема tilt-tray: приём → остановка → поворот → опрокидывание |
| Катящийся товар (пуфик) простреливает лоток насквозь — качение сохраняет энергию | V-ложе + торцевой флап-ловушка |
| Тонкий товар (9 мм) проваливается в щель лента/лоток | Статичный мостик-переходник над шарниром |
| Тонкий товар проваливается в стык плит V-ложа | Плиты внахлёст — шов закрыт |
| Высокий круглый товар (шлем) скатывается с ленты вбок | Высокие борта разгонного участка |
| Плоский круглый товар (тарелка) укатывается «колесом» мимо кейджа | Направляющие юбки-каналы к кейджам |
| Товар зависает на кромке при опрокидывании | Автодожим наклона + событие в лог |
| Открытый флап упирается в пол и клинит наклон | Ограничение угла открытия флапа (78°) |

### 5.2. Кейс микро-габарита: от отказа к конструктиву

Товар «Ручка» (148×13×9 мм) — на 1 мм тоньше минимально допустимого
габарита — последовательно выявил три режима отказа: проваливание в щель
лента/лоток (решено мостиком), проваливание в стык плит V-ложа (решено
плитами внахлёст) и ненадёжный сход с плиты при опрокидывании (масса
~150 г, трение у порога скольжения). Итоговое решение — **пассивный
щелевой отсев**: калиброванная щель 40 мм на мостике-переходнике, через
которую проваливается только товар тоньше минимального габарита — сразу
в реджект-карман категории C, не доходя до накопителя. Это прямая
механическая материализация правила «меньше 10×10×10 мм → C»: категория
таких товаров известна заранее, и им незачем занимать цикл лотка.
Реализован также вибродожим наклона (+-0,6°, 4 Гц) как страховка
для товаров у порога трения.

### 5.3. Программа испытаний

**Юнит-тесты классификатора** (`pytest tests/ -v`, 35 тестов):

- правила: все категории, границы допусков (450/320/10 включительно),
  приоритет «габарит над формой» (негабаритный И круглый → C),
  порог 0,8 включительно, флаг пограничности;
- геометрия на синтетике с аналитическими эталонами: куб (габариты OBB
  восстанавливаются из произвольного поворота), цилиндр и сфера
  (коэффициент > 0,95), эллиптический цилиндр 50/43 (коэффициент 0,86
  аналитически — совпадает), плоский эллипсоид (0,7 — корректно не круг);
- геометрия восприятия: аппроксимация эллипса по полной и частичной
  (окклюзированной) дуге восстанавливает b/a; отклонение прямой;
  анализ облаков точек цилиндра/диска/коробки;
- воспроизводимость (детерминизм повторного расчёта);
- золотой прогон: 11 STL тестового набора против эталонных категорий.

**Стресс-испытания симуляции** (`python -m sim.conveyor_sim --stress`):
на каждый товар — штатная подача плюс два возмущённых варианта
(смещение до ±100 мм от оси ленты и разворот на +25°/−40°),
итого 33 эпизода. Возмущения гасятся штатными средствами
(центрирующие скирты, V-ложе, флап); микро-габаритный товар
при любой ориентации оседает в реджект-кармане отсева (категория C).

**Устойчивость восприятия к ориентации** (`python -m perception.rgbd_pipeline
--poses`): каждый товар измеряется depth-камерами при 5 углах поворота;
**55/55 измерений корректны**, категория постоянна на всех углах.

## 6. Самооценка по шкале уровней готовности (УГТ)

**Ось 1 — глубина проработки части определения и классификации: уровень 4.**
Подход обоснован; работа устойчива и воспроизводима на всём тестовом
наборе (детерминизм зафиксирован сидами); пограничные случаи разобраны
с визуальными доказательствами; ошибки метрики найдены и устранены
(кейс Цилиндра); часть подтверждена в составе целостного решения
(классификация управляет исполнительной частью в симуляции).
Дополнительно замкнут контур восприятия **пиксели → категория**:
классификация по данным виртуальных depth-камер даёт 11/11 совпадений
с эталоном и устойчива к ориентации товара (55/55 измерений).

**Ось 2 — глубина проработки исполнительной части: уровень 3–4.**
Валидация: 11/11 маршрутизаций на полном тестовом наборе.
Детализированный проект: компоновка участка, состав и логика узлов,
циклограмма, расчёт производительности, проработка нештатных ситуаций,
валидированная физическая модель (MuJoCo) с прогоном всего тестового
набора **и проектная документация физического узла** (`docs/PHYSICAL_UNIT.md`):
кинематическая схема, расчёт момента приводов, спецификация (BOM), схема
управления и рабочая прошивка контроллера (`hardware/`), синхронизированная
по углам с симуляцией. До полного уровня 4 остаётся сборка железного
прототипа по этой документации — узел спроектирован «под сборку»
(ESP8266 + 2× MG996R, настольный масштаб 1:3).

## 7. Ограничения решения

- Лента моделируется кинематически (тяга и центрирование при контакте
  с полотном); динамика проскальзывания ленты не моделировалась.
- Зоны C/D — площадки с ограждением; подъём товара в ролл-кейдж
  высотой 800 мм требует детализации (наклонный жёлоб/подиум).
- Коллизии — по выпуклым оболочкам STL (тонкие объекты — габаритным
  боксом); для габаритной классификации это консервативно.
- Симуляция одного товара на участке единовременно; поток с интервалом
  < cycle time требует каскада лотков (см. раздел 3.3).

## 8. Направления развития

1. **Перенос RGB-D-контура на физическую камеру**: виртуальный контур
   восприятия уже работает (раздел 2.6); на реальном сенсоре меняется
   только источник кадров — алгоритмика та же.
2. **Сборка физического прототипа** трёхпозиционного лотка по готовой
   документации `docs/PHYSICAL_UNIT.md` (ESP8266 + сервоприводы; прошивка
   и мост к классификатору уже в `hardware/`).
3. Дискретно-событийная модель потока (AnyLogic) для обоснования
   конфигурации каскада под целевой темп.

## 9. Воспроизводимость

```bash
pip install -r requirements.txt
python -m classifier.run_classification --models data/models --out output
python -m sim.conveyor_sim            # headless; лог: output/sim_log.csv
python -m sim.conveyor_sim --video    # + output/sim_demo.mp4
python -m sim.conveyor_sim --stress   # стресс-прогон вариаций подачи
python -m perception.rgbd_pipeline    # RGB-D: пиксели -> категория (11/11)
python -m perception.rgbd_pipeline --poses  # устойчивость к ориентации
pytest tests/ -v                      # 35 юнит-тестов
```

Все инструменты — открытое ПО из перечня допустимого (Python, MuJoCo,
trimesh, shapely, SciPy, NumPy, matplotlib). Форматы результатов нейтральные:
CSV, PNG, MP4, STL. Управляемые экспертом параметры перечислены в README.
